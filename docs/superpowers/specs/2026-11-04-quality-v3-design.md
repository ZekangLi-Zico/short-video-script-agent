# 第4题：创作质量与可验证修订 v3

用户已授权按上一轮前四项优化，并要求保存旧版、真实需求复测、更新报告。本设计落实该范围，不增加发布、视频生成、多 Agent 或性能工程。

## 目标与边界

1. 在不编造产品事实的前提下，让标题、场景、连接文案适配实际创作需求。
2. 区分时长上限与目标时长；更好满足场景、语言、受众、风格等明确要求。
3. 根据实际反馈局部修订，并记录修改前后、触发反馈、保留内容。不能通过重写所有内容冒充修订有效。
4. 冻结现实需求后评测，区分完成状态、合理停止、实际可用性、错误声明与复算结果。

保留 Python 3.11+ 标准库架构、CLI 和本机网页。无新增依赖。默认决策上限12步，用户可在现有界面选择；评测使用12步。模型仍决定下一动作，宿主绑定参数和完成门槛。

## 方案

保留原严格白名单为 `expression_mode=strict`；新增 `creative`，网页默认使用。旧 JSON 未指定模式仍走 strict，保证原始记录可重放。选择有边界的创作方案，而不继续扩大固定白名单，也不完全移除审核。

事实块继续逐字引用检索到的素材和 fact ID。creative 模式开放标题、画面与无来源连接文案，但这些公开表面全部由独立上下文审核；不相信写稿模型自称“创意”的标签。审核项必须覆盖宿主枚举的每个表面，原文和位置必须一致；分类为普通表达、资料支持的声明、无支持声明、不确定。资料支持的声明必须引用已检索事实。宿主核对引用存在性，语义蕴含仍是模型判断，不能宣称形式化事实证明。硬性禁词仍由本地规则阻断。

将表达审核合入现有需求审核调用，不新增每轮模型调用。输入只有原需求、当前稿、宿主当前规则结果（含可用事实与待审表面），不含写稿历史与自述。creative 需求检查缺少表面、重复位置、伪造来源、不确定或失败时不可完成。场景可为虚构拍摄安排，但产品UI能力、性能、效果、价格必须受素材支持。

`duration_mode=max` 为旧请求默认值，范围(0, target]；`target` 要求 0.9×target 至 target（±上浮不允许，以免突破平台上限）。界面显示“接近目标（90%–100%）”。确定性估时保留原语速和算法，不因过检修改。独立审核还检查无意义停留、重复事实凑时长；有拍摄动作的停留可合理存在。数值区间通过不等于实际配音达标。

每次 write_script 由宿主保存版本摘要：前后哈希、字段差异、未变镜头数、当前失败反馈。镜头按索引比较，明确不是稳定语义ID。模型提示要求保留用户指定标题/结构与已支持事实，对失败定位修订。新稿始终使所有旧检查失效。日志只记录可观察依据，不记录内部思维链。报告、网页过程区显示实际差异。

## 验证与兼容

备份现有交付 ZIP 与当前源码、文档、测试结果；哈希记录全部旧 examples/evaluations/outputs 文件。原始50次及此前修复记录不可覆盖。新增输出放 evaluations/quality-v3-20261104；每次尝试使用唯一目录，保存失败与成功记录，不替换。

开发前冻结12个现实 brief：4个既有回归、8个新需求。需求来自工作语境，不从预期系统状态反推；另存独立评分标准。正式验收的故障注入与数值边界是工程测试，与现实 brief 区分。使用既有4个原始记录和新需求中4个旧版重跑作对照；不是随机试验，也不宣称泛化率。

TDD 覆盖公开接口 ToolBox.call、Agent.run、StructuredModel.review、HTTP/界面请求与证据复算。旧66项测试及旧轨迹复算应保留。新增测试覆盖：声明藏在标题/画面/连接文案，审核漏项/假来源/不确定，时长模式边界，修订后旧检查无效，差异记录与原稿对应，历史输出兼容。

真实模型复测使用冻结输入；新模式仅添加明确的 expression_mode，时长语义由 brief 冻结决定。报告分别统计正常产出、合理缺口、工具/模型故障、步数耗尽及人工评阅，不用 completed 数量冒充成功率。抽样网页验证与批量 CLI 运行分别标注。保留至少两条不同实际行动路径。

## 已知限制与停止条件

素材仍是合成 demo-editor，不是小影真实产品承诺。语义审核与创作使用同一后端独立上下文，存在相关错误；引用ID真实不等于蕴含关系正确。估时不是TTS实测。最多8镜头，简易检索，多轮长期记忆和资料上传不在本轮。出现严重误放行必须修复或明确阻止提交；非关键质量问题如实报告，不无限扩大范围。
