# 05 · 实现复盘与下一步

## 当前v7.3.1：算法升级与证据版本一起管理

最终复核发现：新检索支持精确素材ID后，旧记录中的同一查询会从三张卡变成一张，导致历史验证报错。保存资料快照还不够，复算还依赖工具算法。现在新记录明确写检索契约，旧记录按已有版本选择历史算法，原结果不重写；验证器也会拒绝篡改记录。默认报告另存，避免验证动作覆盖以前的结论。

本次重点是把当前功能、真实验收和提交入口对应起来，避免文档一处写v7、一处写v7.3。具体网页结果及仍需本人提供的交付信息见[当前报告](../evaluations/submission-v7.3.1-20261106/README.md)。GitHub最终上传、本人实际用时仍未代填；本次未增加生成或审核模型阶段。

## v7.2：修复调用链中的无效等待

用户实际使用漫剧资料时暴露收尾与审核超时。保留记录后发现，除了外部服务等待，程序还存在全任务恢复机会过早用尽、审核失败仍发起下一次决策、Windows诊断丢失部分事件的问题。先用失败测试确认这些行为，再有限修复；同时隔离无关工具配置、压缩重复的决策明细。两条原失败输入本轮均完整运行，事实检查和模型修订过程继续保留，详见[修复报告](19-call-reliability.md)。下一步如再遇到失败，应依据新阶段诊断定位，避免盲目加长超时或堆叠重试。

## 历史v7：自然旁白

这轮纠正了把形式检查通过当成稿件可用的倾向。先写连贯讲述，再安排镜头，比不断增加拦截规则更贴近创作者需要。生成改善必须从实际句子和整篇转折验证，报告保留变差或仍生硬的例子。截图还暴露默认页面仍连旧进程，现用后台版本标记和启动核验避免混淆。 见[v7实际报告](17-v7-natural-voice.md)。

这是一份项目实现过程记录，由 AI 辅助整理，不冒充候选人的个人学习经历。

## v6：减少干扰与无用等待

v5把可写性放开后，仍向creative提供strict的四个标题和连接语示例，造成大量套用。本轮从提示输入移除这些干扰，并保留全部当前需求与事实。实际复用四个示例标题的稿件由22份变为0份。

等待也不只是网络问题：每个本地检查之前都在等待模型选择动作。现在一次模型审核动作补齐本地检查，仍由模型读取真实结果选择修订。配合medium推理配置和历史压缩，全部任务耗时中位数由314.1秒降至126.1秒。完整状态变化、退步及例子见 [实际报告](16-v6-titles-latency.md)，不把单次观察当作永久保证。

独立审查发现缓存需同时绑定检索集合，以及取消不能只在步骤开头检查；两者均用失败测试复现后修复。129项测试通过。无需为了这道题加入多Agent编排、复杂队列或数据库。

## v5：让事实约束服务于成稿

这轮最有价值的变化是把“有依据”与“逐字照抄”分开：来源身份和原文可由代码核对，准确改写与翻译交给绑定同一稿件的语义审核。V22与V30因此从停止变为完成。声画分轨也让双语、静音卡和顺序文字有直接可执行的时间安排。

分镜不是给功能清单配背景。V48的入口指引、V45/V47/V49具体动作比原先名词镜头更好用；但V32的具体错字例子被写泛，22份稿复用示例标题，说明提示中的示例仍可能压过场景创作。后续应优先改善成稿的针对性，不继续堆叠审核层。

实际50次结果是36完成、12需补、2超时，与旧版完成数持平。内容评阅21改善、13相当、4退步、12需补；新能力确实完成了旧版受阻的任务，但没有证据说所有需求都更好或运行更稳定。完整对照见 [v5报告](15-v5-effective-scripts.md)。本人投入与独立复验仍需候选人如实补充。

## v4.1 历史复盘

验收脚本也会有漏洞：按已知版本名检查完成证据，增加版本时容易漏检。这轮先用缺失、失败、旧稿审核的反例重现，再将验收条件绑定行为契约。另一个发现是，“说明删掉了什么”服务于创作者，不一定应该成为观众听到的旁白。增加独立审稿备注，让修改解释与视频内容各有位置。

两项改进对应原题的可核验结果与有效修订，不增加生产功能。真实验证使用原始需求及受控故障，旧结果保留；小样本不能证明以后不再犯同类错误。证据、收益和遗留问题见 `12-final-polish-report.md`。候选人可用 `13-reviewer-and-practice-guide.md` 亲自走一遍，不把 AI 整理的复盘当成个人已掌握的经历。

后续50次同输入真实网页复测把定向观察扩展到日常需求：V36/V46正文与备注分离，V31用两张短卡满足限制；整体状态从35完成变成36完成，但响应315→317。新增备注又暴露阶段措辞残留，说明结构分离并不自动保证所有说明始终准确。4次自然清理异常保留了成功响应；翻译、极短表达和估时仍有边界。详见[50次对照复盘](14-v41-real50-comparison.md)。这轮不再改应用，记录问题与收益，避免把一次样本改善宣称为普遍能力提升。

## v4 历史复盘

50次真实实验显示，增加一个审核模型并不自动提高可靠性：审核必须看到绑定同一稿件的工具结果，且理解`hold_seconds`与实际镜头时长的区别。另一项教训是，得到模型响应、执行完工具、保存完记录是不同阶段；非关键的目录清理不能抹去有效响应，最终保存失败也不能显示成功。

本轮以这两类缺陷为边界增加估时上下文和逐步检查点，不扩展到多Agent、数据库或自动发布。复现、修复、真实回归和未解决问题见 [v4报告](10-finite-v4-report.md)。检查点只能保证最后已成功落盘的状态，不能保证硬盘不可写时保存，也不能恢复被杀进程尚未返回的模型调用。

## 最难的问题

**如何证明脚本有依据，而不仅是附带来源 ID。** 如果模型写“效率提升 80%”并引用真实存在的 P01，简单检查 ID 存在会错误放行。早期版本要求逐字引用和批准表达；v5改为保留来源原句、允许准确改写并做语义核对。来源存在性可以机械验证，句子是否真正受原文支持仍需语义判断。

**如何证明改稿后的结果真的重新检查。** 初稿已通过时长检查，并不代表修改后仍然通过。程序在每次更新稿件后清空旧检查，并用内容哈希绑定检查版本，提前完成会成为模型下一步看到的错误观察。

**如何获得真实模型证据。** 离线 Mock 能证明代码流程，却不能证明动态决策。本次保留 Mock 作为无凭证入口，同时通过已登录的 Codex CLI 运行真实模型。遇到旧 CLI 不兼容时保留失败记录，改用现有新版运行程序，不把失败替换为虚构成功。

## 工程收获

- Agent 的效果需要从“观察→后续动作”的记录中评估，只有漂亮的最终脚本不够。
- 负向场景中明确未完成也是正确结果，状态必须与工具证据一致。
- 模型生成负责选择、组织和修订；输入约束、计时和完成门禁由确定性代码保证。
- 证据要同时保留输入、实际输出、工具记录、数据版本和限制，方便复核。

## 历史阶段的下一步计划

有限修复阶段补上了需求覆盖核对与最终解释；v3进一步开放场景创作，保留原严格模式，加入逐表面审核、明确时长语义和实际修订差异。具体效果与保留问题见 `docs/09-quality-v3-report.md`，旧版取舍仍在归档中。

1. v3已增加有边界的创作审核；后续需要独立标注样本和多次重复试验，测量误放行、误拒绝，不能用本轮小样本宣称准确率。
2. 用实际配音时长校准估时参数，对数字、英语、停顿和语速给出更合适的估计。
3. 做多次、多模型重复评估，报告完成率、事实错误率、修订成功率、耗时和用量。
4. 在现有网页基础上支持分镜直接编辑、会话续跑，并补充候选人实际复验记录。
