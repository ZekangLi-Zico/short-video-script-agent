# 第 4 题：有限修复报告

## 目标与结论

本轮按用户要求，以“短视频脚本 Agent”原题验收为目标，只修复完成状态、结果解释和验证证据方面的问题，没有扩成通用视频创作产品。

修复前已有可运行的模型决策循环、三个业务工具、来源校验、超时修订、失败处理、离线入口及提交文档，原八场景验收有实际运行证据。但 50 次现实需求测试暴露出：程序通过来源和时长检查后，仍可能遗漏具体需求并标记 completed；模型解释在最终页面被覆盖。因此不能把“预设验收通过”解释成“所有现实需求都满足”。

修复版增加需求覆盖核对并保留解释，原核心功能的回归结果见下文。对仍受模板或资料限制的要求，更准确地报告未完成，不把这类状态变化说成新增创作能力。GitHub 上传、最终 commit 和评审权限仍未完成，不能宣称已交卷。

## 原题要求与本轮范围

- 按主题、受众、平台、目标时长和风格，利用产品资料与品牌规则生成标题、分镜、旁白/字幕、估算总时长、来源、风险和任务状态。
- 模型根据真实检索、时长、规则结果选择下一步；无资料可改查或请求补充，超时/规则不通过可修订再检查或明确失败。不得编造产品事实。
- 覆盖正常、缺信息、无素材、工具失败、超时修订/失败；保留至少两条动态路径、至少三组输入/实际输出/Trace，并有执行上限。
- 提交代码、测试、README、依赖/环境示例、需求/方案/评估/AI 使用/复盘文档，以及 GitHub URL 和最终 commit SHA。网页是用户追加的人工测试入口，原题不强制 UI、部署、多 Agent 或成片生成。

固定标题、逐字事实块和画面白名单是本项目的实现取舍，**不是原题规定必须如此**。本轮保留这些限制，补上受限时的检查和解释。

## 做了哪些修复，对原题有什么帮助

| 修复 | 修改前的问题 | 当前实现 | 对原题的价值 |
|---|---|---|---|
| 保留最终解释 | completed 时统一成功文案覆盖模型 finish.message，删改原因只在 Trace 中 | 原模型说明进入网页、output.json 和 script.md，另附宿主检查说明 | 评审能直接看到删掉了什么、为什么删、哪些事实无依据；加强风险及任务状态交付 |
| 增加需求覆盖核对 | “有来源且未超时”可能被当作“完整满足需求” | `check_requirements` 使用同后端的新上下文，逐项核对主题、受众、平台、风格，输出原文要求、证据及 met/unmet/uncertain | 补强理解业务需求与有效修订；检查结果可反馈给模型，支持修订或明确停止 |
| 收紧完成条件 | 原完成条件只有来源/规则与时长 | 三项检查均须成功且匹配当前稿；需求核对另绑定原始请求。改稿清空全部旧检查，不确定、失败或未检查不能 completed | 避免跳过检查、旧结论复用和虚报完成，强化工程可靠性 |
| 修正审核缺证据的误拒绝 | 首轮修复复测 T43 时，稿件事实已通过，但需求核对看不到事实依据，错误判为 uncertain | 向核对模型传递绑定当前稿的实际规则检查和原文引用；Trace 记录这份输入，过期检查不传入 | 避免把正确修订反复退回，体现通过实际失败定位、修正并复验；没有单纯放宽“通过”条件 |
| 展示核对和缺口 | 用户需翻原始 Trace 才能判断取舍；部分建议指向不存在的上传入口或内部字段 | 页面显示核对结果与具体依据；提示模型用普通语言说明需要什么材料及当前模板限制 | 让状态和限制可人工复核；页面本身只是辅助展示，不宣称因 UI 自动加分 |
| 调整节奏提示 | 80%–100% 目标比例可能诱导长停留凑时长 | 去掉固定填充比例，要求根据内容安排停留，资料不足时说明缺口 | 更诚实地遵守时长约束；只是提示层改进，未证明剪辑节奏已全面改善 |
| 修正负例验收判断 | 模型启动失败返回 blocked，可能被无素材/不可能时长用例误判通过 | 任一 model_error 均不能代替业务场景证据；无素材必须有实际空检索观察 | 测试真正证明工具反馈和动态决策，避免用无效证据声称通过 |

这些是与原题审核点相关的改进，**没有官方评分细则，不能据此承诺具体加多少分**。最直接的价值是状态更准确、删改依据可见、回归证据可信。

归档限制：两次 T43 曾落入同一临时归档位置，现已按运行 ID 分开，并逐字节核对原始后端产物。首轮提交前/后的页面快照被覆盖，未冒充保留；其结果页面和截图从网页历史重新打开原记录采集，标注于 `ui/T43/archive-note.md`。这没有重跑模型，也没有改变原 50 次测试记录。

### 首次环境失败与证据判断修复

另有一次受限沙盒启动尝试保留在 `examples/repairs/live/`。七个需模型的场景均未成功获得模型响应；当时旧验收判断将其中两个 blocked 错算为负例通过。原索引未改写，新 `audit.json` 中重新评估后仅缺信息前置校验可通过。之后使用正常本机权限重新运行，结果存入不同目录；未改登录凭据，也未偷偷切换 Mock。

真实记录中的模型名为 `CLI configured default`，不推断具体型号。所有素材为合成数据，本轮没有证明真实产品能力、实际配音时长或总体稳定率。

## 未修复及保留的限制

| 项目 | 当前情况与未修复原因 |
|---|---|
| 自由表达与场景画面 | 标题、连接语、visual 白名单和逐字事实引用保留。自定标题、校园/宠物/家庭场景、英文双语、短字卡等仍可能无法完成。扩大创意范围需要区分事实与创作表达并重建语义核验，超出本轮有限修复 |
| 语义核对的误判/漏判 | 新核对仍使用同一后端模型的新上下文。宿主能检查结构、原文引用和哈希，不能证明每条要求都被拆出、判断一定正确；这不是独立模型认证或人工验收 |
| 素材上传与规则编辑 | 网页仍无上传、资料管理和审批入口。只改进说明方式，实际补资料仍需维护者修改本地数据；没有假装补齐操作闭环 |
| 节奏、内容密度、真实时长 | 没有 TTS/成片测时、客观镜头密度评分，也没有重测所有长稿。普通 target_seconds 仍按上限解释；首轮修复正常样例 12.8 秒满足 30 秒上限，但不能据此称为理想的 30 秒视频 |
| 通用检索与多轮追问 | 仍是本地关键词检索和单次有界任务。needs_input 后需补齐输入重新运行，没有跨进程会话续跑 |
| 模型成本与稳定性 | 需求核对多一次模型调用，增加耗时和额度；同一请求仍可能产生不同结果。本轮小样本不能建立成功率、误判率或性能基准 |
| API 与全量回归 | API 只有离线契约测试，未用真实 Key 联调；本轮没有重跑全部 50 条，也未开展多模型、并发或压力测试 |
| 发布交付 | 尚未上传 GitHub、提交新的 commit、配置评审读取权限或点击交卷。旧 SHA 只标识修复前基线，不能作为当前交付的最终 SHA |

生成视频、上线部署、多 Agent、真实发布均未实现；它们不是原题必需项，不因本次修复增加。

## 证据与复现

所有旧测试和新测试分开保存。原 50 次输入在执行前冻结；修复版网页复测直接使用其中 T02、T28、T43 的原始输入，没有根据期望结论修改场景。每次保存实际输入、输出、Trace、素材快照、manifest、Markdown，网页案例另有页面文字、原始结果和截图。

```bash
python -m scripts.run_tests
python -m scripts.evaluate --provider mock --output outputs/recheck-mock
python -m scripts.evaluate --provider codex --output outputs/recheck-live
python -m scripts.audit_repairs
```

前两种验收输出建议写入新目录，避免覆盖此次证据。`audit_repairs` 只读取原冻结目录并向 `examples/repairs/audit.json` 写复核报告；本地复算不重新调用或认证远端模型，不证明需求审核的语义结论正确。
