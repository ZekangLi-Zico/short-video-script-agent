# v7.2 模型调用故障修复

本次处理《城寨风云》资料接入后的模型调用失败，保留已有脚本质量与事实检查。修改前源码和文档存于 `archives/v7.1-before-call-fix-20261106/source.zip`，旧实验文件保持原样。真实模型复测与最终对比见[本轮报告](../evaluations/call-fix-v7.2-20261106/README.md)。

## 故障与修复

用户的人物预告运行 `a4c3fd45ef0243d1a78c8506e5b5228a` 持续851.43秒，以未完成结束。稿件修订后，需求审核等待超时，随后又发生一次决策超时。程序存在四处可确认的改进点：

| 问题 | 本次修改 | 实际作用 |
|---|---|---|
| 每次结构化调用继承与本任务无关的个人工具配置 | 内置服务下使用隔离配置，显式保留模型与服务档位；自定义供应商/profile 继续继承 | 减少无关工具启动；不改变用户的全局配置和登录信息 |
| 决策输入重复携带完整审核明细 | 决策阶段保留结论、失败项、当前稿、检索事实和历史摘要；完整明细仍在独立审核与记录中 | 对该失败状态，任务输入从41809降至25873字节，减少38.1%；不是总模型token数 |
| 全任务仅有一次恢复机会，前面用掉后，后面的审核无法恢复 | 每次调用最多重试一次，全任务最多额外恢复两次；支持超时、服务繁忙与流中断 | 后续审核有恢复机会，仍有明确上限，不重放已执行的业务工具 |
| 审核失败后又继续请求模型决策，Windows 超时诊断缺失部分事件 | 审核恢复失败立即结束并保留草稿；保留终止前收集的事件，提取脱敏计数和错误信号 | 避免无用的后续等待，能区分故障阶段；不保存内部推理、原始错误正文或凭证 |

网页会显示当前正在重试决策还是审核。最终错误区分等待超时、服务繁忙、连接中断、鉴权和限流等已识别原因。异常任务仍标记未完成，不能用“已有草稿”替代完整审核。

## 验证方式

先添加7项故障回归测试，在旧代码上复现4个失败、3个错误，再修复实现。最终147项自动测试全部通过，覆盖 Windows 输出回收、阶段诊断脱敏、恢复预算、审核失败终止、决策输入压缩、配置隔离与自定义供应商兼容。记录见本轮目录中的 `regression-red.txt` 和 `automated-pass/`。

通过网页选择真实 Codex 模型，原样重跑此前失败的“陈峥人物预告”和“门缝里的烛光”。两条输入在开始前存入 `cases.json`，结果不覆盖旧记录；没有把预期答案写进需求。两条均完成，分别耗时285.52秒、121.91秒，共14次响应、零超时；输入与资料哈希保持一致，证据复算均无错误。详细记录见本轮报告。

## 原题要求与边界

模型继续根据真实工具结果决定检索、写稿、审核、修改和结束。完成仍要求当前稿的时长、规则及独立需求审核通过；12步上限不变。该修复改善可运行性、异常记录与复现能力，没有用固定分支代替模型决策，也没有把离线测试当作真实模型效果。

旧记录只说明调用在180秒内未返回，没有足够事件证明每次超时的服务端原因。隔离配置和压缩输入可以减少本地与上下文开销，但不能据此声称已经消除模型服务波动。两条复测属于定向故障回归，不是新的20/50次可靠性统计。人物文案质量、实际配音时长仍应单独人工审阅。

当前 HTTP API 适配器保留原实现，未用真实 API Key 联调；本轮修复重点是实际使用的 Codex 通道。尚未重新制作最终ZIP、推送GitHub或交卷。
